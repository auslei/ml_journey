# ml_journey

A single learning path from linear algebra to LLM fine-tuning. It is training material and a personal reference, and the notebooks feed blog posts, so the explanations matter as much as the code.

Source material is copied from the old folders under `/home/anthony/github_backup/` (`ml_fundamentals`, `machine_learning_model`, `machine_learning_deep_learning`, `python_gensim_nlp`, `Word-Embedding`, `auto_regressive_model`, `llm_finetune`). Those folders are read-only. Never edit or move anything in them.

## Layout

```
01_linear_algebra_calculus/   05_deep_learning/
02_probability/               06_nlp/
03_classical_ml/              07_llm/
04_unsupervised/              common/
```

Each section holds:

- `README.md`: concept map, reading order, what you should be able to explain at the end.
- Numbered notebooks (`01_...ipynb`), read in order.
- `intuition_test.ipynb`: the closing exercise. Questions first, predictions written down before running the code, answers after.
- `tests/`: only where the section has real Python modules (for example `07_llm`).

## Workflow

- Plan first. Explain the reasoning and the impact before writing anything, and implement only after approval.
- Ask when something is unclear. Do not guess.
- Modify only what was requested. Keep each change small and reviewable.
- Work on a feature branch. Commit when a section is done, then ask before merging or pushing.
- Do not reference or modify anything under an `archive/` or `z_archive/` folder.

## Environment

- Use `uv` for everything (`uv add`, `uv lock`, `uv run`). No bare `pip install`.
- Python 3.12. The local default is newer and the TensorFlow/Torch wheels lag behind it.
- One `pyproject.toml` with optional extras: `torch`, `tf`, `llm`. Core sections must run without the heavy extras.
- Keep pinned versions in `uv.lock` so the notebooks still run in a year.

## Deep learning policy

- Keras 3 is the teaching API. It is multi-backend, so the same notebook runs on the PyTorch backend.
- Native PyTorch is used where the training loop itself is the lesson, and for everything in `06_nlp` and `07_llm`.
- TensorFlow-only features (`tf.data`, `GradientTape`) live in an appendix at the end of `05_deep_learning`, not in the main path.

## Notebook standards

- Every notebook follows the same order: intuition, maths, cost function, from-scratch version, library version, tuning, what breaks.
- Prose is short. Explain the idea in a few cells, then show it working. No textbook chapters.
- Strip outputs before committing (`nbstripout`). The notebooks must be reproducible from a clean run, so seed every random call.
- Data is small and downloaded or generated by a script in `common/`. Never commit datasets, trained models or weights.
- Keep a notebook under 30KB after stripping. If it grows past that, split it.
- `print()` is fine in notebooks. In `.py` modules use the standard `logging` module with an info line before each major step.

## Code standards

- `snake_case` for variables and functions, `PascalCase` for classes.
- Type hints on every function signature in `.py` files.
- Ruff for formatting and linting. Keep imports alphabetised and minimal.
- Simple and readable over clever. Short inline comments only where the intent is not obvious.
- Functions are deterministic where possible. Pass a seed, do not rely on global state.
- Raise clear, actionable errors, not raw tracebacks.
- Shared helpers go in `common/`. Sections talk to each other only through `common/`, never by importing from a sibling section.

## Testing

- Notebooks must run end to end (`pytest --nbmake`) before a section is called done.
- Python modules get small, deterministic unit tests in the section's `tests/` folder.
- Where a function has two outcomes, test both. Where it touches input validation, test the bad input.
- Run the full suite, plus `ruff check`, before declaring a section done.

## Writing style

All markdown and notebook prose follows `~/dev/my_voice.md`.

- Short sentences, plain words, no filler. State the point once.
- Australian English spelling (analyse, colour, regularisation).
- No emojis or emoticons in the markdown files or notebooks.
- No em dash overuse, no "it's not X, it's Y" reframes, no self-answered rhetorical questions, no "delve" or "at its core".
- Use numbers to make the argument where there are numbers.
- Close a section with a plain sentence or a real open question, never a generic sign-off.

## Cleanup

Keep `README.md` files current when a section changes. Remove obsolete files straight away rather than leaving them for later.
